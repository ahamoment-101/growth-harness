# Configuration Guide

## Configuration Entry Points and Verification

`wrangler.jsonc` stores Cloudflare resources and public settings. [`shared/config/agent-models.json`](../shared/config/agent-models.json) stores bundled model defaults, Agent assignments and reasoning strengths. Put credentials in ignored `.dev.vars` locally and Cloudflare Secrets in production. `npm run setup` prepares the local file; it does not copy a second model registry. Local `.dev.vars` entries override Wrangler vars, while production never reads this file. File-based configuration works on macOS, Linux and Windows without shell-specific environment commands.

`npm run config:check` validates login and configuration structure. When optional services or model keys are missing, it indicates that the corresponding capability is unconfigured; adding `--require-models` requires all provider keys actually referenced by current models to be present. `npm run config:check:deploy` reads production vars and remote secret **names** without treating local keys as configured online, and verifies that existing admins have at least one bound login method that remains enabled. The check does not verify provider permissions, balances, or network connectivity.

The single login switch is `AUTH_LOGIN_METHODS`: defaults to `password`, and can also be set to `password,google` or `google`. Empty values, unknown methods, or turning off all methods will raise an error. When Google is enabled but configuration is missing, field names are listed requiring completion or removal of `google`, without echoing field values. The frontend and backend share check results; disabled methods do not show buttons, and the backend rejects their login endpoints.

## Login

| Field | Source and Purpose | Required Condition / Impact of Absence |
| --- | --- | --- |
| `AUTH_LOGIN_METHODS` | Choose login methods | Defaults to `password` |
| `AUTH_SETUP_TOKEN` | Initialization code of at least 32 characters generated by `setup` | Required for creating password admin for the first time; cannot initialize without it, cannot be reclaimed once admin is created, used codes can be removed |
| `AUTH_SESSION_SECRET` | Random signing secret generated by `setup` | Required for Google login and GSC authorization status; basic password sessions use random tokens independent of Google |
| `AUTH_GOOGLE_CLIENT_ID` | Client ID of Web OAuth application in [Google Cloud Console](https://console.cloud.google.com/apis/credentials) | Required when Google login is enabled; public vars in production |
| `AUTH_GOOGLE_CLIENT_SECRET` | Secret of the same Google OAuth application | Required when Google login is enabled; stored in Secrets in production |
| `AUTH_ALLOWED_GOOGLE_EMAIL` | Google email allowed to log in or bind by deployer | Required when Google login is enabled, only accepts verified and matching emails; identical emails will not automatically merge accounts |

The Google login callback is `<origin>/api/auth/google/callback`, registered separately for local and production addresses. A password admin can actively bind Google under `/account` while logged in; an original Google admin can set a password here, preserving the same user, workspace, site, and tasks.

Passwords are only stored in D1 as scrypt hashes with random salt, requiring at least 12 characters and at most 1024 UTF-8 bytes. Parameters are N=32768, r=8, p=3, using about 32 MiB per computation; resource and length limits protect authentication costs. Initialization, login, and password change are each rate-limited to 20 attempts per 10 minutes per client IP, with only hashed IPs stored. Password changes and offline resets atomically revoke old sessions in the database. The platform must meet actual password computation and business execution resource requirements.

Basic login does not depend on email delivery services, nor does it claim emails are verified; emails serve as local account identifiers. Forgotten passwords are reset by the deployer, without providing an unauthenticated public reset endpoint. Google OAuth requires configuring applications and callbacks independently and complying with service policies.

## Models

The public distribution defaults to OpenRouter. See [model connections and protocols](model-channel.md) for the version 2 registry and custom endpoints.

| Field | Service and Purpose | Required Condition |
| --- | --- | --- |
| `shared/config/agent-models.json` | Bundled connections, model capabilities, Agent assignments and reasoning strengths | Already supplied; defaults require only an OpenRouter model key |
| `MODEL_REGISTRY` | Optional complete replacement for the bundled model configuration | Only for deployment-specific or local overrides |
| `OPENROUTER_API_KEY` | OpenRouter account credential | Required only when a selected profile uses the sample `openrouter` connection |
| `OPENAI_API_KEY` | OpenAI account credential | Required only when a selected profile uses the sample `openai` connection |
| `ANTHROPIC_API_KEY` | Anthropic account credential | Required only when a selected profile uses the sample `anthropic` connection |
| Custom name referenced by `apiKeyEnv` | Credential for your own compatible endpoint | Required only for selected connections; CLI checks and secret upload read the registry dynamically |

Keys belong in ignored `.dev.vars` locally and Cloudflare Secrets in deployment. They never belong in `agent-models.json`, `MODEL_REGISTRY`, source control, frontend settings, or logs. Only keys referenced by the default and per-Agent profiles are required. Selecting a model does not prove the account has access or that the endpoint accepts its tool schema; verify the full writing workflow.

For a local-only model selection, an optional `MODEL_REGISTRY` in `.dev.vars` must contain a complete version 2 registry as single-line JSON. Precedence is local override → Wrangler override → bundled JSON, with each override replacing the complete registry rather than merging individual fields. Remove a stale override to use the lower-priority configuration again, and restart the dev server after changes. No credential is silently borrowed from another connection.

## Optional Services

| Field | Corresponding Service / Purpose | When Needed and Impact of Absence |
| --- | --- | --- |
| `FIRECRAWL_API_KEY` | [Firecrawl](https://www.firecrawl.dev/): scraping, search, and external research | Required when using related tools; when missing, corresponding operations return missing configuration while other features remain available, billed by provider |
| `FIRECRAWL_RESEARCH_MODEL` | Firecrawl research model, sample `spark-2` | Used by managed research, must be a vendor-supported model |
| `FIRECRAWL_RESEARCH_MAX_CREDITS` | Vendor credit limit for a single research job, sample 100 | Not cumulative Agent round limit; cumulative consumption is tracked separately |
| `DATAFORSEO_LOGIN`, `DATAFORSEO_PASSWORD` | API login and API password for [DataForSEO](https://app.dataforseo.com/) | Both enable optional paid Keyword Research Agent queries; without them, existing research methods remain available and unavailable metrics stay unknown |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Search Console OAuth app in Google Cloud | Required when using GSC, callback `<origin>/api/gsc/oauth/callback`. Independent of backend Google login; when using the same app, two callbacks must be registered |
| `GSC_TOKEN_CIPHER_KEY` | Self-generated 32 random bytes, formatted as 64-character hex | Required for GSC refresh token encryption; direct rotation renders existing tokens indecipherable and requires migration first |
| `AUTH_SESSION_SECRET` | Signing secret mentioned above | Also required by GSC, regardless of whether Google login is enabled |
| `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN` | [Cloudflare](https://dash.cloudflare.com/) runtime custom domain / route read-only checks | Corresponding diagnostics require read-only permissions; Wrangler OAuth deployments do not require passing deployer tokens to the Worker |
| `CLOUDFLARE_WORKER_NAME` | Deployed Worker script name used by custom-domain route diagnostics | Keep equal to `wrangler.jsonc` name; missing diagnostics configuration reports an error without overwriting the saved connection state |
| `CNAME_TARGET` | Hostname of your Worker, without `https://` | Used for custom domain DNS instructions; when missing, maintainer domains are no longer displayed, and existing exact Worker Routes can be checked independently |
| `INDEXNOW_KEY` | Self-generated and consistent verification key | Optional publishing notification, absence does not imply indexing or growth performance commitments |

Webhook URLs, headers, and secrets are configured on each site configuration page; they belong to the site rather than global required keys; hosted article publishing does not rely on webhooks. Export secrets are currently stored in D1, and public site APIs only return whether they are configured without exposing values.

Startup checks report missing fields and remediation steps to developers. The Worker also validates login configuration to prevent accidentally exposing endpoints by bypassing the CLI. Standard users see incomplete configuration notices; permission denials, insufficient quota, and unsupported protocols are handled via original tool and Runtime mechanisms without the configuration module deciding strategy for Agents or faking success.

Legacy `AI_GATEWAY_ACCOUNT_ID` and `AI_GATEWAY_NAME` are currently not read by model direct connection paths and do not need to be populated for open-source installations.

## DataForSEO in the Keyword Research Agent

[DataForSEO](https://dataforseo.com/) is a paid API service that supplies SEO data. The Keyword Research Agent can use it to look up country-specific search volume, keyword difficulty, search intent, CPC and monthly search trends, or retrieve organic Google results and results-page features (SERP). These observations help the Agent compare demand and inspect competing pages; they do not guarantee rankings or traffic.

To enable these queries, set both `DATAFORSEO_LOGIN` and `DATAFORSEO_PASSWORD` using the API credentials from your [DataForSEO dashboard](https://app.dataforseo.com/). Put them in `.dev.vars` locally or Cloudflare Secrets in production, then restart or redeploy. Do not commit credentials. No separate feature flag is required. The Agent decides whether a query is useful; configuring credentials does not force a paid lookup on every task.

**Without DataForSEO**, keyword research retains its existing methods: autocomplete suggestions, existing library and business/research materials, web search through Firecrawl when configured, and Search Console data when connected. There is no automatic replacement service for measured search volume or difficulty. Unavailable metrics remain unknown, not zero, and missing DataForSEO credentials do not prevent the Agent from maintaining the library or returning its research outcome. Firecrawl, GSC and model services keep their own setup requirements.

Successful queries are saved by site, language and country with source, observation time and request cost. The Agent can read saved observations before deciding whether fresh data is needed. DataForSEO bills queries separately, including some failures and queries with no data. Interrupted requests with an unknown outcome are not automatically repeated. Existing running tasks keep their pinned tool contract; start a new keyword research task to use the newly added tools after upgrading.
