# Generic Human Work Requests and Workflow Cards

## Integrating New Types

The shared entry point is `createWorkRequest(context, handlerId, node)` in `worker/agent-work/requests.ts`. Business domains create requests through their own semantic tools, passing in the execution context's scoped DB, Task, and publicly displayed content; bypassing execution fences by switching to a database without execution credentials is not allowed. The request id, version, and attribution are generated by the host. Identical id/version and original text can be replayed, whereas altering the content of the same identity reports a conflict; when a revision is needed, close the old request and use a new identity.

Simply register `{ id, respond }` in `WORK_PROVIDERS`, without needing to implement `pending` or `read`:

- `id` matches the prefix of the request id; applicable Agents can be specified.
- `respond` is responsible for business authorization, latest status/version verification, and idempotent side effects; use the incoming command ID to recognize replays and verify the original receipt.
- Throw an error when interrupted and side effects are unknown, retaining the original request and original input to continue verifying the same operation; do not change identity to blindly repeat effects.
- After returning the handling receipt, the shared module saves the receipt and closes the request within the same transaction. Task archives, needs-attention lists, workflow cards, and bubbles automatically read the request status.
- When a business domain completes/withdraws a request via another entry point, use `resolveWorkRequest(context, requestId, observedVersion)` to close it synchronously; this method does not execute business side effects. Historical original questions are retained.
- All declared inputs are saved in the raw response record and displayed on the response node according to field labels; no longer assuming there are only note/value fields.

`createWorkRequest` is a host interface, not a newly added unconstrained model tool. Tools integrated into an Agent are still determined by domain definitions and cannot bypass existing waiting-for-input, publication approvals, or execution permissions.

## Lifecycle and Ownership

`agent_work_requests` uses Task/request as its identity, persisting handler, observed version, pending/resolved, public nodes, and timestamps. The UI only recognizes nodes, materials, fields, and actions, without understanding business semantics such as budget or topic selection. Scoping originates from the Task, and all reads are filtered by workspace, site, and Agent ownership. Requests from cancelled tasks cannot generate new business actions.

The shared layer deterministically guarantees identity, exact input, declared fields, concurrent claiming, persistent receipts, and display status; why it must wait, what legal choices the user has, and what constitutes successful approval remain the responsibility of domain definitions and handlers. Newly added types can declare different materials, fields, and actions without modifying the Runtime main loop, pending queries, or renderer.

Existing Runtime, topic selection, and article reviews still use original domain tables as the authoritative source, retaining `pending/read` compatibility adapters; this update does not backfill old requests currently being processed, nor does it change approval and Runtime state machines. Subsequent write entry points in respective domains can adopt the new request entry points one by one; this is not a claim that all existing business has switched to persistent request tables.

## Card Design

Retains the classroom's existing fonts, light panels, and purple primary actions. Neutral cards carry content; warm colors are used solely for waiting state badges. Title and timestamp form the first layer; body text follows immediately; materials are presented in standalone expandable rows; the input area is grouped away from materials with fine dividers; actions are content-width buttons with descriptions following their respective actions. Required conditions for specific actions or optional notes are shown next to inputs.

Cards override document-level Markdown full-page padding while retaining 16px internal spacing within materials. Desktop card padding is 22/24px, narrow screen is 16px; 12–20px separates content groups, and inputs have a minimum height of 76px. CSS variables are scoped to `.aw-node` and do not alter typography on other document pages.
