# Agent Event Pool and Pre-Publication Review

This document describes the event pool contract. Database objects are in `migrations/0074_agent_event_pool.sql`; migrations and Worker deployments must be checked independently for each installation.

## Protocol

`agent_pool_events` stores immutable event facts, site scopes, object, and version references; `agent_event_types` registers types and protocol versions; `agent_event_subscriptions` stores role-to-type mappings; `agent_event_deliveries` stores delivery and processing states independent to each subscriber. The initial version includes two types: `content.article_ready_for_publication_review` and `agent.task_report_ready`. Subscriptions only determine visible events and do not grant tool or subtask execution permissions.

When an article transitions from other states to `awaiting_review`, D1 triggers save events and subscription deliveries identified by `job_id + artifact_id` in the same write transaction. Updating to a new draft version creates a separate event and obsoletes unclaimed old deliveries; manually moving an article out of the pending-review state also obsoletes unclaimed deliveries. Migrations ingest existing pending-review articles that carry formal draft references into the pool all at once. Database triggers only store facts and do not launch Workflows.

Non-running checkpoints of specialized subtasks can produce `agent.task_report_ready`, targeting and binding to the original parent Run. Legacy Leader Runs retain the original reporting entry point; new Leader Runs accept event pool deliveries. Newly created Leaders use version 3 for tool manifests and prompts, while saved legacy tool manifests remain unchanged.

Each subscribed Agent module registers its own wakeup adapter. The initial version Leader routes publication events without target sessions to the site's fixed "Publication Review" conversation; subtask reports still return to their original conversations. The controller attempts delivery after the review checkpoint and falls back to daily reads of due deliveries. Only pending records in the index trigger a Run; an empty pool does not invoke models. Each read fetches up to 20 items for a single Run; checkpoints in the same Run will continue claiming the next batch. Delivered but unresolved events are reminded again the next day; reading the message itself does not count as completion. Subtask reports are evaluated via `read_task` and then explicitly resolved by `complete_inbox_event`.

## Decisions and Permissions

Upon receiving a publication event, the Leader reads the review conclusion and the article, then calls `decide_publication` to choose publication or reject with specific feedback. Publishing reruns pre-publication structural checks, binds the current `artifact_id`, complete `versions_json`, and persistent operation ID, and subsequently proceeds through the original publication Workflow; the tool receipt only indicates entry into the publication pipeline. Rejecting marks the current draft as rejected, restores the article's writing status, and dispatches a revision task to the original content group. When critical human facts are required, the Leader uses the existing `request_human_input`, allowing other events to continue.

Deterministic code only executes site isolation, version consistency, operational identity, idempotency, objective QA, and current state checks. Draft quality, whether risks permit publication, whether to reject or request information are judged by the Leader. The shared transaction pool does not embed SEO, content quality, or publication strategies; Agent business tools remain registered within their respective definitions. For new types, producers define facts and versions, subscription mappings select receiving roles, and that role module provides the wakeup mechanism—no rewriting of the Runtime loop is required.

## Read Cost and Recovery

Global due queries read bounded pages partitioned by status using the `(status, available_at, event_id, agent_id)` index; single-Run queries use the `(target_run_id, status, available_at, event_id)` index. Events only store short summaries and references, without duplicating article body text. Legacy history does not participate in empty-pool polling. Event writes share transactions with business states; failed wakeups retain deliveries; interrupted executions recover using the same Run, same event, and tool operation receipts. Existing `site_changes` remains solely responsible for real-time UI refreshes and does not act as a business delivery queue.

Verification must cover migration execution, pool ingestion and subscription deduplication, obsolete versions, original-parent routing, message read receipts, query plans, article-version races, publication replay and real child dispatch after rejection. Isolated Miniflare can exercise Worker, D1, Workflow and Pi loops using synthetic model replies; that does not establish real-model review quality or deployed publication.
